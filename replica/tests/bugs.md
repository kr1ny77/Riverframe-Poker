## BUG-009 — Равные даты ответов меняют последнюю оценку по UUID

- Серьёзность: **S3**, неверная последняя оценка и порядок окна попыток при одинаковой дате; исходные попытки сохраняются.
- Сценарий: REG-09; Swift Testing, реальный PracticeHistory schema5.
- Шаги: записать неправильный и затем правильный ответ одной задачи pot odds с одной датой; первый UUID FFFFFFFF-FFFF-4FFF-8FFF-FFFFFFFFFFFF, второй00000000-0000-4000-8000-000000000000; построить снимок курса; сохранить/загрузить архив.
- Ожидание: последний правильный ответ даёт latestCorrect1; порядок наблюдений соответствует записи.
- Факт: сортировка равных дат по строке UUID перемещала прежний неправильный ответ в конец и давала latestCorrect0.
- Доказательство: [детерминированный падающий тест](evidence/BUG-009-before.txt), courseEqualDatesPreserveRecordedOrder. Исходный общий прогон также воспроизвёл нестабильность в courseAccuracyDenominatorsAndTopicIsolation: [лог](evidence/regression-lessons-unit-before.txt).
- Исправление: LearningCourseSnapshot сортирует по дате, затем индексу записи. Наблюдения одного урока поступают из одной коллекции. Контрольный пример раздельных знаменателей получил фиксированные различные даты для проверки изменения физического порядка архива.
- Повтор: [детерминированный тест](evidence/BUG-009-after.txt)1/1 PASS; [полная регрессия ядра и приложения](evidence/regression-lessons-core-after.txt)40/40 Swift Testing,24/24 Core и build/Application-checks. Независимый разбор изменения подтвердил семантику пяти коллекций и сохранения.
- Статус: **исправлен**. Игровая модель и дизайн сохранили хеши; Git в Poker отсутствует, commit-ID отсутствует.


## BUG-001 — После ошибки reload запись уничтожает исходную повреждённую историю

- Серьёзность: **S1**, потеря исходных локальных данных.
- Сценарий: F03-N2; PracticeStore.reload/record.
- Окружение: macOS, реальный атомарный JSON store, изолированный временный файл.
- Шаги: создать store и записать попытку; заменить файл строкой `corrupted-after-successful-load`; вызвать reload; убедиться в сообщении ошибки; попытаться записать новый ответ.
- Ожидание: исходные байты сохраняются, запись блокируется до успешной загрузки или явного clear.
- Факт до исправления: catch в reload устанавливал только errorMessage; loadFailed оставалсяfalse, record заменял файл новым JSON.
- Доказательство: [падающая проверка](evidence/BUG-001-before.txt), `Tools/AppChecks.swift --reload-regression`.
- Исправление: `App/Persistence/PracticeStore.swift`: при ошибке reload устанавливается loadFailed=true. Успешный reload вновь разрешает запись.
- Повтор: [успешная проверка](evidence/BUG-001-after.txt); новая попытка после восстановления сохраняется один раз. Core24/24 также прошёл после изменения.
- Статус: **исправлен**, регрессионная проверка сохранена в Tools/AppChecks.swift и вызывается Tools/verify.sh.

## BUG-002 — Проверочный скрипт не находит модуль после перехода на Swift6.4

- Серьёзность: **S3**, автоматическая проверка блокируется, ручная сборка приложения доступна.
- Сценарий: запуск Tools/verify.sh на текущем Xcode27.1/Swift6.4.
- Шаги: выполнить `./Tools/verify.sh`; Core проходит, iOS build проходит; этап компиляции Application-checks использует жёсткий `.build/debug/Modules` и glob старых object files.
- Ожидание: Application-checks собирается из текущего SwiftPM build output.
- Факт: `no such module 'PokerCore'`; новый Swift Build размещает модуль и PokerCore.o в `.build/out/Products/Debug`.
- Доказательство: [baseline.txt](evidence/baseline.txt).
- Исправление: `Tools/verify.sh` использует `swift build --show-bin-path`, оба расположения modules и оба типа object layout; добавляет запуск Swift Testing и reload-regression.
- Повтор: [full-verification.txt](evidence/full-verification.txt) включает успешные Application checks и regression BUG-001.
- Статус: **исправлен**. Совместимость со старым layout предусмотрена ветвью скрипта; повторное выполнение на старом Xcode в этом окружении недоступно.

## BUG-003 — Debug-сборка для конкретного симулятора запрашивает несовместимую архитектуру

- Серьёзность: **S2**, запуск выбранной Debug-конфигурации блокировался; generic build при этом проходил.
- Сценарий: native simulator build/test, Apple Silicon, iPhone17e iOS27.0.
- Шаги: xcodebuild с destination конкретного iPhone17e, Debug, исходным проектным build settings; локальный PokerCore собирается дляarm64, app также пытается собраться дляx86_64.
- Ожидание: текущая Debug-сборка и зависимости используют активную архитектуру выбранного устройства.
- Факт: SwiftDriver PokerTrainer x86_64 не разрешает arm64 PokerCore; `Unable to resolve module dependency: PokerCore`.
- Доказательство: [ui-first.txt](evidence/ui-first.txt), [ui-first.xcresult](evidence/ui-first.xcresult).
- Исправление: `PokerTrainer.xcodeproj/project.pbxproj`: проектная Debug-конфигурация ONLY_ACTIVE_ARCH=YES. Release-конфигурация сохраняет общий build profile.
- Повтор: [ui-run.txt](evidence/ui-run.txt) — app и UI-runner собраны для выбранного симулятора; итог выполнения сценариев приведён в report.md.
- Статус: **исправлен в настройках сборки**; проверку запуска см. report.md.
